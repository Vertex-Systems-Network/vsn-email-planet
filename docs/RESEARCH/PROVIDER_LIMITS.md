# Initial provider limits and evidence

Reviewed 2026-11-10 against official docs. These sources do not replace account-specific capability probes or a live sandbox check.

| Provider | Evidence-backed constraint | Product implication | Source |
|---|---|---|---|
| Gmail sync | Initial sync or missing partial history needs full sync; history records are only retained for a limited period. An expired/out-of-date `startHistoryId` may return HTTP 404; Gmail says perform a full sync. | Per-mailbox durable cursor, controlled full reconcile, atomic merge/cursor advancement, duplicate-safe message identity. | https://developers.google.com/workspace/gmail/api/guides/sync ; https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list |
| Gmail OAuth | Choose narrow scopes; restricted scopes involve verification; server-side storage/transmission of restricted-scope user data requires security assessment. | Consent and launch gate must be surfaced; metadata-only scope is distinct from body access. | https://developers.google.com/workspace/gmail/api/auth/scopes |
| Microsoft Graph mail | Graph accesses a user's mail with appropriate delegated or application permission; shared mailboxes are supported; in-place archive mailboxes are not supported in Graph Mail API according to overview. | Model delegated/app permissions and shared mailbox routes; do not claim archive coverage without a distinct route. | https://learn.microsoft.com/en-us/graph/api/resources/mail-api-overview?view=graph-rest-1.0 |
| Microsoft Graph permissions | Shared mail scopes are permission- and account-type-specific; some application permissions require admin consent. | Capability manifest records exact permission type/admin consent; test shared mailbox boundaries. | https://learn.microsoft.com/en-us/graph/permissions-reference?view=graph-rest-1.0 |
| Graph lifecycle | Lifecycle events include `reauthorizationRequired`, `subscriptionRemoved`, and `missed`; ignoring them can break notification flow. | Handle lifecycle events and authoritative delta reconciliation; webhook receipt alone is not sync proof. | https://learn.microsoft.com/en-us/graph/change-notifications-lifecycle-events |
| cPanel UAPI | UAPI accesses cPanel account features; disabling roles can disable associated API functions. cPanel's docs recommend UAPI over deprecated cPanel API 2. API token calls can operate using account data. | Use operation-level UAPI only; discover host/account permissions and role disablement; avoid deprecated API2; token rights are not blanket mailbox content consent. | https://api.docs.cpanel.net/cpanel/introduction ; https://api.docs.cpanel.net/cpanel/tokens ; https://api.docs.cpanel.net/cpanel-api-2/cpanel-api-2-modules-email/cpanel-api-2-functions-email-addpop |
| OAuth | RFC 9700 is the current OAuth 2.0 Security BCP and deprecates insecure modes. | PKCE/state/nonce, exact redirects, modern token handling and documented threat review before provider auth. | https://www.rfc-editor.org/rfc/rfc9700.html |

Open: endpoint-level UAPI methods/role coverage, host-specific API restrictions, provider admin consent verification, IMAP OAuth/TLS matrix and live behavior. No sandbox credentials were supplied; no live provider test has occurred.

## Message deletion, mailbox removal, and retention review

Reviewed 2026-11-10 from current official provider documentation. The endpoint behavior below is not a universal data-erasure promise; retention, backup, hold, and server-version behavior must be checked for the target account/server.

| Provider and operation | Documented permission and effect | Retention/erasure boundary | Safe product behavior |
|---|---|---|---|
| Gmail `users.messages.trash` | Moves one message to Trash; accepts `gmail.modify` or `mail.google.com` OAuth scope. | Trash is a reversible state, not proof of erasure. | Offer as the reversible default; record message ID and operation receipt. |
| Gmail `users.messages.delete` | Permanently deletes one message without an undo; requires the restricted `https://mail.google.com/` scope. Google's method documentation explicitly prefers `messages.trash`. | The API call's success is not a claim about independent exports, Vault retention, or backups. Workspace policy must be considered separately. | Treat as a separately consented high-impact capability; do not request the broader scope for routine trash actions. |
| Gmail / Google Workspace user deletion | Directory API `users.delete` requires `admin.directory.user`; Google documents that a user on a Vault legal hold cannot be deleted. | A deleted user can be undeleted for 20 days when conditions are met; held mail remains preserved in Vault even after it disappears from the user's view. Vault retention rules are configured in Vault, and holds require Vault privileges/matter access. | Separate mailbox/message deletion from identity deletion. Require explicit admin scope and confirmation; discover/document hold state where authorized. A successful API response or 20-day recovery window does not establish permanent erasure. |
| cPanel UAPI `Email::delete_pop` (legacy API2 `Email::delpop`) | Current cPanel API guidance recommends `Email::delete_pop`; deprecated API2 `delpop` documentation says deleting the email account deletes the account and all its data. | The cited documentation does not specify host backup/snapshot retention or an erasure timeline. API2 response text also references removed Horde data, so do not infer modern host-level purge behavior from that legacy response. | Prefer installed UAPI and verify its response on the specific cPanel version. Treat mailbox deletion as a destructive account operation; do not call it verified erasure of backups or copies. |
| Exchange Online via Graph `DELETE message` | Least-privileged permission is `Mail.ReadWrite` for delegated and application access. Graph warns deletion can be unavailable for items already in Recoverable Items/Deletions. | Exchange Online normally retains permanently deleted items in Recoverable Items for 14 days; an administrator can configure up to 30 days, and litigation/in-place holds override ordinary purge timing. | Distinguish moving/deleting from final erasure; disclose unknown tenant retention/hold state and never promise a purge date from the Graph response alone. |
| Exchange Online via Graph `message/permanentDelete` | Least-privileged permission is `Mail.ReadWrite` for delegated and application access; moves the item to Recoverable Items/Purges. | Microsoft says the item becomes permanently deleted after a period unless a hold exists. Graph's `204` is not proof that the retention engine has purged it. | Require a separate explicit approval; report `requested/permanent-delete API accepted`, not `data erased`, until an authoritative policy-aware confirmation exists. |
| Plesk Obsidian XML API `mail.remove` | Administrator may remove any Plesk mail account; a customer may remove accounts only for sites belonging to that customer. The operation can remove multiple accounts on one site. | The API describes account removal and success/error status; the cited endpoint does not specify mailbox file, backup, snapshot, or legal-hold erasure timing. | Scope targets by site and account; treat account removal as destructive and do not label it message-content erasure. Probe server version and retention/backup policy separately. |
| DirectAdmin legacy `CMD_API_POP` delete | The legacy docs identify `action=delete` with a domain and virtual POP user. Current docs say each server exposes its supported API schema at `/static/swagger.json`; dedicated Login Keys can limit permitted actions and source IPs. Admin impersonation and reseller-managed-user boundaries are role dependent. | The cited account API does not specify stored-message purge, backup retention, or hold behavior; legacy/current endpoint coverage differs by installed version. | Prefer the installed server's current API schema; use dedicated restricted Login Keys and least-privileged user/reseller contexts. Treat account deletion as unverified erasure until that host's storage/backup behavior is established. |

### 2026-11-10 permission/retention delta

- Google Workspace user deletion is an administrative identity operation, distinct from Gmail message deletion. The Directory API requires `admin.directory.user`; Google explicitly refuses to delete a user under Vault legal hold. Deleted users may be restorable for 20 days under stated conditions, and Vault holds preserve covered messages outside the user's view. Do not infer mailbox erasure from either user deletion or API success.
- cPanel's deprecated API2 mailbox-delete page states account data deletion and points to UAPI `Email::delete_pop`; it does not document backup/snapshot purge. The current endpoint's behavior and authorization still need a version-specific probe, so host-level erasure remains unknown.
- No provider tenant policy, Vault hold, cPanel server, customer mailbox, or sandbox was accessed. This is a documentation-only update; buyer validation and runtime capability evidence remain open.
